# #4 — Паралельний entity-tracking (БЕЗПЕЧНИЙ дизайн, ще не реалізовано)

Статус: **дизайн готовий, реалізація чекає тесту з реальними гравцями.**
Чому не запушено всліпу: див. «Застереження».

## Що це
`ChunkMap.tick()` (main-потік) щотіку ітерує ВСІ tracked-ентіті й для кожного:
1. якщо ентіті змінив section → `updatePlayers(allPlayers)` (видимість + spawn/despawn-пакети),
2. `serverEntity.sendChanges()` (дельти руху до гравців, що його бачать),
3. якщо гравці зміщувались → другий прохід `updatePlayers(movedPlayers)` для всіх ентіті.
Вартість ≈ O(ентіті × гравці). На main, серіально.

## Безпечний алгоритм (партиціонування по регіону-власнику)
Кожен ентіті належить рівно одному регіону → його `TrackedEntity` чіпає лише потік цього регіону. Тоді:

**Фаза A (паралельно, per-region work-round):** кожен region-потік для СВОЇХ ентіті:
- обчислює зміну section, `updatePlayers(allPlayers)` при зміні, `sendChanges()`;
- зміщених гравців-ентіті складає у **потокобезпечну** колекцію (ConcurrentLinkedQueue).
**Бар'єр.**
**Фаза B (паралельно):** якщо зібрано зміщених гравців → кожен region-потік `updatePlayers(movedPlayers)` для своїх ентіті.

Диспетчеризація через наявний `RegionThreadPool.runWorkRound(Map<Region,List<Runnable>>)`.

## Чому це потокобезпечно
- `TrackedEntity.seenBy`, `serverEntity` — **per-entity**, чіпає один потік (партиція). ✓
- `player.connection.send()` — **Netty channel write потокобезпечний** (серіалізується всередині); порядок пакетів РІЗНИХ ентіті до одного гравця неважливий. ✓
- `level.players()`, `distanceManager` — **лише читання**, стабільні в цій фазі. ✓
- `entityMap` НЕ мутується під час фаз (spawn/despawn вже відкладені на main — [[deferred-spawn]]). ✓
- Ентіті НЕ тікають у цій фазі (позиції стабільні після entity-round). ✓

## Застереження (чому не зроблено всліпу)
1. **Цінність ∝ к-сть гравців.** Spark: на ядрі main припаркований ~113с (простоює) — tracking на main НЕ вузьке місце поки гравців мало. Виграє лише populated-сервер. **Спершу виміряти** (див. нижче).
2. **Mod-ризик:** `Entity.startSeenByPlayer()` / pairing модових ентіті — перевизначувані, можуть чіпати спільний модовий стан. Це поверхня, яку видно ЛИШЕ наживо з гравцями.
3. **Непротестовність соло:** без гравців tracking=0 → паралельний шлях не покривається тестом. Баги (привиди-ентіті, дублі-спавни) видно лише наживо.

## План впровадження (коли є гравці для тесту)
1. Спершу **виміряти** реальну вартість tracking'у на populated-сервері (інструментація фази).
2. Якщо tracking > ~5мс/тік → реалізувати за дизайном вище, **за прапором** `-Dnestworld.parallelEntityTracking=true` (дефолт OFF → нуль ризику для дефолтної поведінки).
3. Тест: 2+ гравці бачать рух/спавн/деспавн мобів коректно; жодних привидів/дублів; стрес ~1000 ентіті в полі зору.
4. A/B main-час tracking фази on/off.

Пов'язане: [[deferred-spawn]] (той самий принцип — мутації ChunkMap лише на main).
