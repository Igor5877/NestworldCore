# PERF-1B — Mod API end-to-end performance validation — audit + spec DRAFT

**Status: DRAFT for owner review (2026-10-05).** No code yet. The governing TZ is
`PERF-1B-tz.md` (owner's full text of 2026-10-05). PERF-1A W2 official is pending on host quiet;
PERF-1B work does not use the benchmark cores until its pilot.

## 1. Audit: what exists today

**Facade.** `net.nestworld.modapi.entity.NestWorldEntities.setVelocity(Entity, Vec3)`:
- **fire-and-forget:** no return value and no exception in any documented case;
- the backend is chosen by `VelocityBackendRegistry.current()`;
- outcomes such as target missing or a stale intent are silent no-ops to the caller.

The consumer therefore cannot observe acceptance or outcome. "Accepted" equals "submitted" (the
API has no rejection), and every outcome count must come from the providers.

**Forge provider** (`projects/modapi`, `ForgeVelocityExecution`):
- captures (dimension, uuid) before the marshal and reacquires on the server thread;
- applies with the LATEST_INTENT_WINS tracker (`SetVelocityIntentTracker`).

The stock-Forge plus external-provider setup already runs in `tests/modapi-compat/run-matrix.sh`
(upstream installer 47.4.20, provider jar `nestworld-modapi-provider-1.0.0-SNAPSHOT.jar`).

**NestWorld provider** (`NestworldVelocityBackend`) → `EntityMutationDispatcher.dispatch`. The
paths map onto the TZ modes:

| Caller thread | Path in `dispatch` | TZ mode |
|---|---|---|
| region thread that owns the target | `applyDirect` ("same-region direct") | **B2** owner fast path |
| another region's thread | `nestworldSendOrQueue` → cross-region mailbox → owner applies | **B3** mailbox |
| main thread | `nestworldPostMessage` → owner mailbox; `applyDirect` if the owner mailbox is ≥ the backpressure threshold | B3, with a backpressure branch |
| unmanaged level or no owner | `applyDirect` | out of scope |

Reroute: hop-limited redelivery when the owner changed in flight (existing Core behaviour).

**Outcomes** (`EntityMutationDispatcher.ApplyOutcome`): APPLIED, STALE_INTENT_DROPPED,
INCARNATION_MISMATCH, TARGET_REMOVED, TARGET_NOT_PLAYER. Mailbox terminals (TARGET_NOT_FOUND,
REDELIVERY_LIMIT_DROPPED) are counted in `MailboxLifecycle`.

**Gap.** There are no aggregated low-overhead counters per path (owner-fast / mailbox / reroute /
backpressure-direct) or per ApplyOutcome, on either provider. Today they are visible only through
per-operation `ApiOpTrace` logging (forbidden in primary measurement, TZ §6) or `MailboxAudit`
(mailbox path only, behind a flag the owner kept off for the primary matrix).

## 2. Decisions needed before implementation (owner)

**Decided (owner, 2026-10-05): N ≤ 8 in every matrix** (PERF-1B and W2). The CPU layout stays as
in PERF-1A: 8 benchmark cores (CPUs 2–9) plus 1 housekeeping core (CPU 1), with siblings 19–27
kept idle.

**D1. Path and outcome counters.** TZ §6, §9 and §10 require aggregated attribution and closed
accounting; nothing in 47.4.264 provides them.
- *Recommendation:* add instrumentation-only counters (LongAdder per path and per ApplyOutcome)
  in `EntityMutationDispatcher` / `NestworldVelocityBackend` and in the Forge provider, exposed by
  a command, with **no behaviour change**.
- This is a Core change, so PERF-1B needs a new trusted build (integrity / canary / smoke) under
  the TZ's "newer trusted build only by separate decision" clause. A PERF-1A comparison then needs
  the TZ §27 A/B overhead check (counters on vs off).
- *Alternative without a Core change:* the consumer verifies final state only. That keeps
  LATEST_INTENT_WINS correctness, but gives no applied-throughput or path attribution, so it
  cannot meet TZ §6 / §9.

**D2. Where B0 and B1 run.**
- *Recommendation:* B0 (raw `setDeltaMovement`) and B1 (Mod API on the Forge provider) on a
  **stock Forge server** (upstream 47.4.20 plus the external provider, as in the compat matrix);
  B2 / B3 on NestWorld 47.4.26x.
- The same consumer jar runs everywhere. B0 is a consumer mode switch (config) that calls the
  vanilla method instead of the API: same jar, different code path, recorded per run.

**D3. Producer topology** (TZ §17: no unfair producers). Operations are generated by a
consumer-owned **ticking block entity** (ordinary Forge BlockEntity) placed in every cell. Each
tick it calls `setVelocity` on K target mobs, with a version-increasing velocity.
- **Same producers everywhere:** identical count, placement and per-tick rate on Forge and on
  NestWorld. On Forge they tick serially on the server thread; on NestWorld, on region threads.
  The difference comes only from the execution model.
- **B2:** targets in the producer's own cell, so the owner is the caller's region, giving the
  owner fast path.
- **B3:** targets in a fixed partner cell (another region), giving the cross-region mailbox.
- Topology is reused from the frozen W1: 16 sealed cells, marker-built layout, interference /
  JIT / warmup discipline. Each cell holds K target mobs plus the producer BE. This is not W1
  (TZ §8): the primary metric is API operations.

**D4. Primary metric** (fixed before the pilot, TZ §11): accepted operations reaching an
accounted terminal state per measurement second (APPLIED + STALE_INTENT_DROPPED + TARGET_* +
mailbox terminals), taken from the D1 counters. Submitted/s and applied/s are also kept.

**D5. Latency** (TZ §12): accepted → terminal. This needs a timestamp at accept and at terminal.
- *Proposal:* the consumer stamps the submit time into the intent version. The provider counter
  records sampled latency into a fixed histogram (for example 1-in-64 sampling, HdrHistogram-style
  log buckets) instead of logging per operation.
- This is part of the D1 instrumentation change.

**D6. Rates.** A saturation test (backlog to find capacity) and a sustainable test (bounded
queue) are separate series and are never pooled (TZ §20). The pilot sets K and the per-tick rate.
