# NeoForge 1.21.1 Adapter Portability — Phase A Scoping / Readiness Audit

**Phase A only — no code changed, no NeoForge MDK fetched, no implementation task opened.** Per
the user's explicit instruction: this answers "is Core even capable of a second Adapter without a
rewrite," not "port the server." Phase B (actual port) is out of scope until this document's open
question is resolved.

## Q1 — What is the 1.20.1 Adapter surface, exactly?

Turned out to be **four** mechanisms, not the two (`patches/`, `net.nestworld.adapter`) assumed
going in:

| # | Mechanism | Size | Nature |
|---|---|---|---|
| 1 | `patches/` | 709 files | Vanilla `net.minecraft.*` diffs, regenerated by `genPatches`. Mixes Forge's own MDK baseline patches with NestWorld's insertions in a single cumulative diff per file — the two cannot be cleanly separated by diffing alone. |
| 2 | `net.nestworld.adapter` | 6 files | This session's new pure-Java Adapter package (#96/#97). Thin static wrappers only. |
| 3 | **Vendored Forge source** (`src/main/java/net/minecraftforge/`) | 652 files | **New finding.** Forge's own upstream source, checked in wholesale as ordinary buildable source — this is how the "hybrid-arch" fork edits Forge's *own* classes directly (not just vanilla Minecraft) without a second patch-diff mechanism. Of 652, only **4** are actually NestWorld-modified: `GameData.java` (startup profiler marks + ModernFix compat check + a state-cache parallelization — the shipped StateDefinition win), `LanguageHook.java` (lenient malformed-lang-JSON parsing), `ServerModLoader.java` (startup profiler marks), `RegistryManager.java` (added a `nestworldDumpAll` diagnostic method). The other 648 files are stock Forge, present only because the build needs them. |
| 4 | Direct `net.minecraftforge` references inside `net.nestworld.*` proper | 8 files | Precise, exhaustive grep (not sampled): `NestworldCompat`/`NestworldCommand` (`ModList.get()` lookups — trivial), `ModCallbackClassifier`/`ModCallbackAttribution` (string-prefix package-name checks, not an API dependency at all), `NestworldRegionSystem` (the real Adapter entry point: `TickEvent`, `ServerStartingEvent`, `ServerStoppingEvent`, `SubscribeEvent`, `RegisterCommandsEvent`, `EntityJoinLevelEvent`, `EntityLeaveLevelEvent`, `ITeleporter`), `NestworldMod` (`@Mod` bootstrap + static `MinecraftForge.EVENT_BUS`), `NestworldCommand` (also one `RegistryManager.nestworldDumpAll` call), `CrossRegionCapabilityBus` (`Capability`/`LazyOptional` — already flagged in #95 as the priority debt item), `EntityInteractionAdapter` (`ForgeHooks.onInteractEntityAt` — already isolated by #97). |

## Q2 — Where does Core directly depend on Forge?

Cross-referenced against #95's CORE tags: **exactly one** CORE-tagged file has deep Forge-API
coupling — `CrossRegionCapabilityBus` (`Capability`/`LazyOptional`), already tracked debt.
`NestworldRegionSystem`/`NestworldMod` are CORE+ADAPTER *by design* — they're the literal
orchestrator entry points, expected to touch Forge's event bus, not a violation. Everything else
touching Forge from Core-adjacent code is a one-line utility call (`ModList.get().isLoaded(...)`),
not real coupling.

## Q3 — Which classes are genuinely version-specific (1.20.1 Minecraft API shape)?

- The 73 vanilla files NestWorld hooked into (patches + direct vendored-source edits) each need
  re-verification against 1.21.1's method signatures/obfuscation, independent of loader.
- Known high-risk semantic change: the **ItemStack Data Components rewrite** (landed ~1.20.5/1.21,
  NBT-based item metadata replaced by a typed `DataComponentMap`). Affects any code reading/writing
  item NBT directly. NestWorld's own dispatcher adapters (`PlayerUseItemAdapter`,
  `PlayerUseItemOnBlockAdapter`) only pass `ItemStack` through to vanilla methods plus call the
  stable `getCount()`/`setCount()` accessors — *likely* unaffected, but **not verified against real
  1.21.1 source**, since none is checked out in this environment.
- **Cannot fully answer this question with certainty right now** — this is the honest gap in this
  pass, not glossed over: a real answer needs an actual 1.21.1 source tree/mappings present to diff
  the 73 files against, which does not exist locally (only the 1.20.1 Forge `projects/` trees do).

## Q4 — Which classes are loader-specific (Forge vs. NeoForge)?

- `CrossRegionCapabilityBus` — NeoForge fully replaced Forge's Capability system (registry-based,
  no `LazyOptional`) around MC 1.20.4+, well before 1.21.1. **Semantic rewrite, not a rename.**
- `EntityInteractionAdapter`'s `ForgeHooks.onInteractEntityAt` — NeoForge has an equivalent hook
  under a different class/package. Mechanical port, already isolated to one file.
- `NestworldMod` — NeoForge moved from a static `MinecraftForge.EVENT_BUS` singleton to a per-mod
  *injected* `IEventBus`. **Semantic**, not just a rename (registration model changes).
- `NestworldRegionSystem` — NeoForge kept a broadly similar event taxonomy but renamed the package
  root (`net.minecraftforge.event.*` → `net.neoforged.neoforge.event.*`, `SubscribeEvent` moved to
  `net.neoforged.bus.api`). Mostly mechanical for the entity-join/leave/command events used here;
  `TickEvent`'s shape specifically is worth flagging — NeoForge split it further
  (`ServerTickEvent.Pre`/`.Post` etc.) rather than a 1:1 rename.
- The **vendored-Forge-source technique** (652-file tree, 4 modified) — this entire mechanism has
  no NeoForge equivalent in the same shape; NeoForge's own source lives under a different package
  root and structure. The 4 real modifications would need to be re-derived against whatever
  NeoForge's equivalent classes are, file by file — genuinely bespoke, not mechanical.
- `ModList`/string-prefix checks — trivial, NeoForge ships an equivalent `ModList`.

## Q5/Q6 — Semantic vs. naming-only changes (1.21.1 NeoForge)

**High confidence** (well-established, from training knowledge, not verified against local source):
- Forge `Capability<T>`+`LazyOptional` → NeoForge Capabilities = **semantic**
- Static `EVENT_BUS` → per-mod injected `IEventBus` = **semantic**
- `net.minecraftforge.*` → `net.neoforged.*` = mostly **naming**, but not a clean 1:1 — some
  classes were restructured/merged/split during the Forge/NeoForge divergence, not purely renamed
- ItemStack NBT → DataComponents = **semantic**, actually a *Minecraft-version* change (1.20.5/1.21)
  that happens to arrive bundled with the loader move in practice, since Forge itself never shipped
  a 1.21.x release

**Low confidence / explicit gap** — cannot verify from this environment:
- Exact method-signature/obfuscation drift in the 73 vanilla-touched files
- Whether `LevelTicks`/`DistanceManager`/`ChunkMap`/light-engine internals changed shape between
  1.20.1 and 1.21.1 in ways that matter to NestWorld's hooks — no confident specific recollection
  either way, and asserting "no changes" without checking would be exactly the false confidence
  this scoping pass is supposed to avoid.

**This is the real blocker on finishing Phase A properly**: closing Q3/Q5/Q6 needs an actual
NeoForge 1.21.1 MDK/source checked out locally to diff against — none exists in this environment
yet (only the 1.20.1 Forge `projects/` trees do; matches the existing memory note that 1.21.1/
NeoForge work to date has been "research-only").

## Q7 — Can Core run as `Core → Adapter(NeoForge 1.21.1)` without a second Core?

**Preliminary: probably yes for the large majority of Core**, conditional on the Q3/Q5/Q6 gap above
not hiding a surprise. Region/execution/scheduling/ownership/mailbox logic has near-zero Forge
coupling — #95's audit found exactly one CORE file (`CrossRegionCapabilityBus`) with deep Forge-API
usage. The real risk concentrates in three already-identified, already-scoped areas, none of which
touch Core execution semantics:

1. `CrossRegionCapabilityBus`'s Capability system (semantic rewrite, one file)
2. The vendored-Forge-source technique (4 files: `GameData`/`LanguageHook`/`ServerModLoader`/
   `RegistryManager`) — needs re-deriving where equivalent hooks live in NeoForge's own source
3. `NestworldMod`/`NestworldRegionSystem`'s event-bus wiring (mechanical-but-nontrivial: static→
   injected bus, package renames, `TickEvent` reshaping)

## GREEN / YELLOW / RED — preliminary call

**Leaning GREEN**, stated as preliminary, not final: the Adapter surface is small and already
mostly isolated (6 clean dispatcher adapters, 1 flagged Capability file, 4 small vendored-Forge
edits, 8 total Forge-touching files in `net.nestworld.*` proper out of 136). Nothing found so far
suggests Core itself (regions/scheduler/ownership/mailbox/split-merge) would need to change. The
call is preliminary because Q3/Q5/Q6's vanilla-version-diff piece is genuinely unverified — a real
GREEN/YELLOW/RED verdict needs that gap closed first, not asserted from confidence alone.
